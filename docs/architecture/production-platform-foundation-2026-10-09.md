# Nashr — توثيق التقدم والرؤية والخطة التنفيذية

**نوع الوثيقة:** ملحق توثيقي جديد للرؤية والخطة التنفيذية  
**تاريخ التوثيق:** 2026-10-09  
**المرجع البرمجي الذي بُني عليه التوثيق:** `main` عند commit `36bbc39b933cb4f476a0afbc135aa58e90914bb1` — `Pin editorial prompt version to ProductionJob`  
**المرحلة المستهدفة:** `Production Platform Foundation`  
**حالة الوثيقة:** مرجع إضافي؛ لا يستبدل ولا يعدّل الوثائق السابقة.

## 1. الغرض من هذه الوثيقة

تسجل هذه الوثيقة ما وصل إليه Nashr، والرؤية المعمارية المعتمدة، والفجوات المتبقية، والخطة التنفيذية التالية. وهي **إضافة جديدة مستقلة** إلى الوثائق الموجودة؛ لا يُقصد بها إعادة كتابة `current-baseline.md` أو `target-architecture.md` أو `foundation-roadmap.md` أو وثيقة تثبيت القالب.

تجمع الوثيقة بين:
- خط الأساس المعماري بعد PR #68.
- فحص النسخة المنشورة بتاريخ 2026-10-09.
- القرار التنفيذي للمرحلة التالية.
- إضافات تشغيلية اعتمدت من المراجعة: إظهار حالة الإنتاج ومصدرية نتائجه للمستخدم، وتثبيت رحلة Browser E2E، وإضافة خط أساس للأداء والجاهزية دون تحويلها إلى مشاريع مستقلة.

**حدود الإثبات:** وصف ما نُفذ في الكود مستند إلى خط الأساس المشار إليه. وأرقام البيانات والأزمنة أدناه هي لقطة وقت الفحص المنشور، وليست ضمانًا للحالة الحالية. أما العناصر المستقبلية فهي أهداف وخطة، وليست ادعاءً بأنها منفذة.

## 2. الرؤية المعتمدة

يتطور Nashr من مسار إنتاج ناجح من كتاب إلى منشورات Telegram إلى **منصة إنتاج معرفي قابلة لإعادة الاستخدام**. ويمثل هذا التحول **التزام البناء الحالي**؛ فنحن لا نؤجل تنفيذ عناصر الرؤية إلى أن تظهر حاجة تجارية جديدة، بل ننفذها وفق مراحل واضحة ومتعاقبة ضمن هذه الخطة. تستورد المنصة المصادر، وتنظم المعرفة المستخرجة، وتستخدم سياقًا تحريريًا ووصفة إنتاج محددين، ثم تنتج مخرجات قابلة للتتبع والمراجعة والاعتماد والتوزيع.

المبدأ الأساسي هو أن اختلاف المنتجات والهويات والوصفات وأنواع المخرجات يجب أن يُعبّر عنه عبر الإعدادات والعقود والقدرات والمراحل المعروفة، لا عبر نسخ محرك الإنتاج لكل منتج. بناء هذه القدرة العامة جزء من تنفيذ الرؤية المعتمدة، وليس توسعًا اختياريًا ينتظر طلبًا تجاريًا.

المسار المستهدف:

```text
Sources
  → Library / Knowledge Inventory
  → Control Plane
  → Recipe
  → Production Run
  → Artifact
  → Review / Approval
  → Product / Publication
  → Distribution
  → Publication Ledger
```

المسار الحالي `BOOK_TO_TELEGRAM_POST` يبقى الوصفة الأولى، ويستمر السلوك الحالي ما لم يكن التغيير لازمًا لتحقيق وضوح أفضل أو مصدرية أو إعادة استخدام.

## 3. المبادئ والقيود المعمارية

1. **المصدر ليس المعرفة، والمعرفة ليست المحتوى.** تُحفظ علاقة المصدر بالمواد المكتشفة وبالمخرجات المنتجة.
2. **الهوية ليست Prompt.** الهوية تصف الغاية والجمهور والصوت والمبادئ؛ والـPrompt مكوّن ضمن سياق الإنتاج.
3. **السياسة ليست كودًا اعتباطيًا.** تكون السياسة إعدادات وصفية يفسرها Validator أو Capability معروفة. لا يُنفذ Python أو SQL من قاعدة البيانات.
4. **الوصفة ليست لغة برمجة.** تصف مراحل معروفة ومسموحًا بها، وتستخدم capabilities مسجلة بعقود وإعدادات محددة.
5. **ثبات سياق العملية.** لا تغيّر الإصدارات المنشورة لاحقًا سياق Run بدأ بالفعل؛ يجب أن تستخدم إعادة المحاولة والاستئناف الـsnapshot نفسه.
6. **الحفاظ على المسار الحالي.** لا حذف لـ`Post`، ولا إعادة بناء للمراجعة أو الجدولة أو النشر، ولا migration هدامة بلا مبرر معماري موثق.
7. **تنفيذ الرؤية على مراحل إلزامية.** كل مكوّن محدد في Target Architecture وFoundation Roadmap يُنفذ ضمن المرحلة المعتمدة له؛ لا يُحوّل إلى خيار ينتظر ظهور حاجة تجارية. يجوز ترتيب المراحل وفق الاعتماديات وبوابات القبول، لا إسقاط أهدافها.
8. **بنية تشغيل متناسبة مع التصميم.** تُبنى الحدود والقدرات المطلوبة الآن داخل Modular Monolith؛ لا تُضاف Microservices أو Redis/Kafka/Celery أو بنية طوابير جديدة ما لم تنص الخطة المعمارية على ضرورة تشغيلية لها.
9. **لا تجريد بلا مسؤولية واضحة.** لا يُستخدم هذا المبدأ لتأجيل مفاهيم Artifact أو Product أو أنواع المخرجات المتعددة؛ فهذه أجزاء من الرؤية المعتمدة. المقصود أن تكون لكل طبقة وظيفة وعقد ومستهلك معروف ضمن التصميم، وأن نتجنب الطبقات المكررة أو الوهمية.
10. **الدليل التشغيلي شرط للقبول.** نجاح اختبارات الوحدة أو استجابة HTTP لا يكفي وحده لإثبات الرحلة كاملة.
11. **المستخدم يرى الحالة والإجراء التالي.** لا يُطلب منه فهم تفاصيل البنية الداخلية أو قراءة stack trace كي يستعيد العملية.

## 4. ما وصلنا إليه

### 4.1 الأساس الوظيفي

يتضمن النظام الحالي:
- FastAPI وSQLAlchemy وPostgreSQL وAlembic ضمن Modular Monolith.
- إدارة المصادر وPDF، وBook Map، ومخزون المواد المعرفية.
- عمليات اكتشاف وإنتاج محفوظة الحالة مع آليات retry/recovery في المسارات المنفذة.
- `ProductionJob` و`ProductionJobItem` لإدارة إنتاج المحتوى الحالي.
- `Post` بوصفه كيان المنشور التحريري الحالي، مع المسودة والتحرير والمراجعة والاعتماد.
- الجدولة والنشر إلى Telegram وسجل النشر.
- مساحات منفصلة وظيفيًا للمكتبة ومصنع المحتوى والنشر.
- واجهات React/Vite/TanStack Query لمساحتي بنك المنشورات والنشر، مع بقاء المكتبة على واجهتها الحالية.
- اختبارات خلفية وواجهات وPlaywright بحسب خط الأساس الموجود.

### 4.2 Control Plane والقوالب

أُسس Control Plane لإدارة Prompt Templates ذات الإصدارات، مع حالات دورة حياة `DRAFT` و`PUBLISHED` و`ARCHIVED`، وresolver يربط القالب بمسار الإنتاج. وأظهر فحص النسخة المنشورة أن `/control` يعرض بيانات حقيقية، وأن `editorial.drafter` كان عند `v5 PUBLISHED` وقت الفحص؛ هذه حالة وقتية وليست قيمة ثابتة يجب افتراضها لاحقًا.

### 4.3 ما أضافه PR #68

يثبت PR #68 `editorial_prompt_key` و`editorial_prompt_version` وجسم القالب المستخدم داخل `ProductionJob` عند الإنشاء. وتستخدم عناصر العملية وإعادة المحاولة والاستئناف النسخة المثبتة بدل حل النسخة المنشورة الحالية من جديد. كما أن العمليات القديمة التي لا تملك provenance للقالب لا ينبغي أن تُنسب إليها نسخة تاريخية بالتخمين؛ يتعامل معها التنفيذ صراحةً بوصفها غير مثبتة.

هذا أول تطبيق فعلي لمبدأ **snapshot سياق الإنتاج عند الإنشاء**. ولا يعني ذلك أن هوية أو سياسة أو وصفة أو عقد مخرج عام قد نُفذ بالفعل.

### 4.4 حالة النسخة المنشورة وقت الفحص

في فحص 2026-10-09:
- كانت `/control` و`/posts/workspace` و`/publishing` والمسارات الأساسية المذكورة في تقرير الفحص تستجيب.
- ظهرت بيانات تشغيل فعلية للمنشورات والمصادر وخطط النشر.
- سُجلت أكثر من 1400 منشور، و28 خطة نشر، و9 منشورات معتمدة ومؤهلة للنشر في لقطة الفحص.
- ظهرت حالات مصادر مثل `FAILED` و`STORED` ومواد غير مكتملة، بما يثبت الحاجة إلى عرض دورة حياة واضحة لا مجرد تخزين الحالة.
- كان `/` يعيد 404، وكان `/health` يعيد `status: ok` دون إثبات جاهزية قاعدة البيانات والاعتماديات.
- كانت قياسات الأداء أولية ومحدودة ولا تكفي وحدها للحكم على throughput أو لتبرير تحسين واسع.

لا يجوز تفسير هذه الملاحظات على أنها إثبات بأن كل Run اكتمل بنجاح، أو أن رحلة Browser كاملة حتى Publication Ledger قد اختُبرت، أو أن pinning التاريخي قابل للعرض للمستخدم. تلك نقاط تتطلب اختبارات وأدلة إضافية.

## 5. ما لم يكتمل بعد

| المجال | الحالة |
|---|---|
| Control Plane | إدارة Prompt Templates موجودة؛ Identity وPolicy وRecipe وOutput Contract بإصدارات مستقلة لم تكتمل. |
| سياق الإنتاج | تثبيت Prompt موجود؛ لم يُعمم بعد إلى `ResolvedProductionContext` أو snapshot عام مضبوط المخطط. |
| Production Run | `ProductionJob` دائم للمسار الحالي، لكنه ليس بعد محرك تشغيل عام مستقل عن منطق Post. |
| Artifact | يوجد عقد أولي؛ لم تكتمل بعد دورة حفظ Artifact دائم ومصدرية كاملة مستقلة عن Post. |
| Product | لا توجد طبقة Product مكتملة؛ وهي جزء معتمد من Target Architecture وFoundation Roadmap، ويجب تنفيذها في مرحلتها المحددة بعد تثبيت حدود Artifact وRecipe. لا تُسقط ولا تُعلّق على طلب تجاري جديد. |
| Distribution | Telegram هو المسار الفعلي؛ العقد العام واختباره عبر Fake adapter يحتاجان إلى الإكمال. |
| واجهة المصدرية | لا تعرض الواجهة بعد snapshot الخاص بالـJob/Run والإصدارات التي أنتجت النتيجة بالصورة المطلوبة. |
| دورة حياة العمليات | يلزم توحيد عرض التقدم والحالات والأسباب والإجراء التالي. |
| رحلة المتصفح | لا يوجد إثبات كامل لرحلة Browser E2E من رفع المصدر حتى Publication Ledger. |
| الأداء والجاهزية | لا يوجد بعد خط أساس موثوق cold/warm أو فحص readiness يثبت جاهزية الاعتماديات. |

هذه فجوات في تحقيق الرؤية، وليست مبررًا لإيقاف المسار الحالي أو لإعادة بنائه من الصفر.

## 6. التصميم المستهدف

### 6.1 Control Plane بإصدارات

تُنفذ المفاهيم التالية ضمن مراحل هذه الخطة، بالترتيب الذي يحدده التنفيذ والاعتماديات، لا بوصفها عناصر مؤجلة إلى ظهور حاجة خارجية:
- `Identity / IdentityVersion`
- `Policy / PolicyVersion`
- `Recipe / RecipeVersion`
- `OutputContract / OutputContractVersion`
- `PromptTemplate / PromptTemplateVersion`

تستخدم دورة حياة موحدة وواضحة. لا يُسمح بتعديل إصدار منشور في مكانه؛ أي تعديل ينتج إصدار Draft جديدًا. ولا تُخزن الأسرار أو كود قابل للتنفيذ في هذه الإعدادات.

### 6.2 ResolvedProductionContext

بدل إضافة نسخ متكررة من جسم كل إعداد إلى حقول منفصلة بلا نهاية، يُعرّف سياق إنتاج مضبوط المخطط يثبت عند إنشاء العملية. يتضمن معرّفات الإصدارات الصريحة والـpayload الفعلي المطلوب لإعادة تفسير العملية، مع معلومات المصدر/اختيار المعرفة والمزود/النموذج حين تكون مؤثرة في إعادة الإنتاج والتحقيق.

يجب التمييز بين:
- الإصدار المنشور حاليًا.
- الإصدار المثبت على العملية.
- المعلومات التاريخية المعروفة أو غير المتوفرة.

إذا كان عنصر مطلوب غير منشور أو غير صالح، تُرفض العملية برسالة صريحة بدل اختيار قيمة تخمينية. ويظل التوافق مع حقول Prompt الحالية قائمًا أثناء الانتقال.

### 6.3 Recipe Engine وProduction Run

تُشغل الوصفة عبر مراحل مسجلة ومحدودة مثل:
`RETRIEVE → SELECT → TRANSFORM → GENERATE → VALIDATE → RENDER`.

لا تسمح الوصفة بتنفيذ كود اعتباطي. يُبنى `ProductionRun` واحتياج عناصره وأحداثه بصورة دائمة وقابلة للاستئناف، مع تقدم على مستوى العنصر، وأخطاء ومحاولات وتوقيتات. يبقى `ProductionJob` الحالي مسار توافق أو تمثيلًا تطبيقيًا أثناء الانتقال، ولا يُحذف في هذه المرحلة.

### 6.4 Artifact وPost وأنواع المخرجات

`Artifact` هو التجريد العام للمخرج، وليس `Post` ولا نوعًا نصيًا فقط. يجب بناء نموذج وعقود تدعم أنواعًا متعددة من المخرجات ضمن الرؤية المعتمدة، بما فيها النص والمنشور والمقال والصورة والفيديو والصوت والكاروسيل والنشرة والدرس ومكونات المنتج التعليمي. تُنفذ هذه القدرة عبر مراحل الخطة؛ ولا يعني ذلك ضرورة تنفيذ كل مولّد متخصص في PR واحد.

يحتوي Artifact على الأقل على نوع المخرج، ومحتواه أو مرجعه التخزيني، وحالته، ومصدر المعرفة، وعملية الإنتاج، وسياق الإصدارات المؤثرة، وprovenance، وتوقيت الإنشاء. يجب أن يسمح التصميم بإضافة أنواع جديدة عبر عقود وقدرات مناسبة دون إعادة تصميم القلب أو جعل `Post` شرطًا على المحرك.

يبقى `Post` التمثيل التحريري الحالي والمتوافق مع المراجعة والجدولة والنشر. يُربط بـArtifact عبر انتقال مرحلي غير هدام، مع الحفاظ على سلوك Review وScheduling وPublication وعدم نقل ملكيتها دفعة واحدة.

### 6.5 Distribution

يُعرّف port عام للتوزيع مع عقد واضح للحمولة والنتيجة ومحاولة النشر. يبقى Telegram أول adapter في المرحلة الحالية، ويُختبر العقد نفسه باستخدام Fake adapter. أما القناة الثانية فتأتي في مرحلة التوسع التالية بعد إغلاق الأساس، وفق ترتيب الخطة، وليس باعتبارها شرطًا لتأجيل بناء حدود التوزيع الحالية. يجب الحفاظ على idempotency حتى لا يؤدي retry إلى تكرار النشر.

## 7. الخطة التنفيذية المعتمدة

تُنفذ الحزم التالية بالتتابع داخل مرحلة واحدة اسمها **Production Platform Foundation**. لا تُعلن المرحلة مكتملة بمجرد دمج كل حزمة على حدة؛ بل عند تحقق بوابة القبول النهائية.

### الحزمة A — خط الأساس وملكية العقود

- إعادة التحقق من `main` ومسار الإنتاج الفعلي قبل التغيير.
- كتابة ADR/عقد يحدد مالك كل مفهوم وحدود المسؤولية.
- تحديد مخططات إعدادات Identity/Policy/Recipe/Output Contract.
- إضافة اختبارات للعقود.
- حماية عقود `Post` وSchedule وPublication من التغيير غير الضروري.

**النجاح:** لكل مفهوم owner وعقد واختبار، ولا توجد ملكية مزدوجة غير مبررة.

### الحزمة B — قابلية فهم عمليات الإنتاج للمستخدم

- عرض Run/Job ID والحالة والتقدم والأعداد المكتملة والفاشلة.
- عرض القالب المثبت والإصدارات المتاحة في snapshot الفعلي، لا الاكتفاء بالإصدار المنشور حاليًا.
- توضيح سبب الفشل والإجراء التالي الممكن.
- تمييز حالات `FAILED` و`STORED` و`PENDING` و`COMPLETED` وفق دلالاتها الفعلية.
- توفير وصول من النتيجة إلى المصدر والمادة المعرفية المرتبطة بها.

**النجاح:** يستطيع المستخدم فهم ما حدث لعملية الإنتاج ومعرفة ما يمكن فعله دون فحص السجلات يدويًا.

### الحزمة C — سياق الإنتاج المثبت

- تصميم `ResolvedProductionContext` أو snapshot JSONB مضبوط schema، مع IDs وإصدارات صريحة.
- تعميم نمط PR #68 دون نسخ غير منضبط للحقول.
- تثبيت السياق المطلوب عند إنشاء Run.
- الحفاظ على السياق نفسه عند retry/resume/recovery.
- إضافة اختبارات لتغيير الإصدار المنشور أثناء استمرار Run وللعمليات القديمة غير المثبتة.

**النجاح:** لا تتغير العملية القديمة عند نشر إصدار جديد، ولا تُخمن الإصدارات التاريخية.

### الحزمة D — Recipe Engine وProduction Run

- فصل orchestration العام عن التفاصيل الخاصة بإنتاج Post.
- بناء stage runner محدود بالـcapabilities المعروفة.
- تحويل `BOOK_TO_TELEGRAM_POST` إلى أول مستهلك فعلي للوصفة.
- توفير progress وretry وresume وrecovery على مستوى العناصر.
- إبقاء Gemini خلف adapter وسياسة إعادة المحاولة الحالية.
- عدم إدخال بنية queue جديدة في هذه المرحلة.

**النجاح:** يعمل المسار الحالي من خلال حدود الوصفة العامة دون نسخ المحرك أو تغيير سلوك المنتج بلا داعٍ.

### الحزمة E — Artifact وProvenance وعقود الأنواع المتعددة

- تنفيذ Artifact بوصفه كيان المخرج العام الدائم، لا مجرد غلاف اختياري حول Post.
- تعريف Output Contracts typed للمخرجات النصية والصورية والفيديو والصوت وغيرها من الأنواع المحددة في الرؤية.
- ربط Post بالمخرج الحالي تدريجيًا دون migration هدامة، مع الحفاظ على سلوك المراجعة والجدولة والنشر.
- تسجيل المصدر والمادة وعملية الإنتاج وإصدارات الإعدادات المؤثرة لكل مخرج.
- توفير storage references ومعلومات النوع والحالة والتحقق الملائم لكل مخرج.
- إظهار provenance في الواجهة وواجهات القراءة.
- تجهيز حدود المحرك والـadapters لدعم قدرات إنشاء مختلفة دون إدخال تنفيذ خاص بكل نوع داخل orchestration العام.
- دعم التحقيق في اختلاف المخرجات دون ادعاء إعادة إنتاج حتمية لنماذج احتمالية.

**النجاح:** يصبح Artifact حدًا عامًا فعليًا يدعم عقود الأنواع المتعددة، ويمكن تتبع كل مخرج جديد إلى مصدره وسياق إنتاجه. تُنفذ مولدات الصور والفيديو والصوت وفق المراحل المعتمدة أدناه، لا باعتبارها أفكارًا مؤجلة لحين ظهور حاجة جديدة.

### الحزمة F — رحلة Browser E2E والجاهزية التشغيلية

إثبات الرحلة التالية عبر المتصفح والخلفية وقاعدة بيانات PostgreSQL:

```text
Upload Source
 → Discovery
 → Select Material
 → Run Recipe
 → Draft / Artifact
 → Edit
 → Approve
 → Publishing
 → Schedule
 → Execute
 → Publication Ledger
```

ويشمل ذلك:
- FakePublisher على حد التوزيع للاختبارات، دون إرسال Telegram حقيقي.
- اختبار الفشل والاستئناف وإعادة التشغيل ومنع النشر المكرر.
- إدخال Library تدريجيًا ضمن واجهة المتصفح المتكاملة دون إعادة كتابة منطق الأعمال.
- structured logs وcorrelation IDs وعدم تسجيل الأسرار.
- health/readiness يميز بين liveness وجاهزية الاعتماديات.
- قياس baseline أولي للأداء البارد والدافئ وطلبات الصفحات وواجهات API الأساسية.
- معالجة مسار `/` الذي كان يعيد 404 وقت الفحص، بتحويل واضح أو صفحة دخول.

**النجاح:** رحلة المستخدم كاملة مثبتة، والحالات والأخطاء قابلة للتتبع، والجاهزية والأداء مقاسان بقدر يسمح بقرارات واقعية.

### الحزمة G — إثبات العمومية وتثبيت خطة المنتجات متعددة الأنواع

- تنفيذ Recipe ثانية حقيقية بعد نجاح الوصفة الأولى والرحلة الكاملة؛ هذه بوابة إلزامية لإثبات عمومية المحرك.
- تحديد منتجات ومخرجات تمثل أنواعًا مختلفة، وليس مجرد تنويعات نصية: منتج نصي/منشورات، ومنتج صور، ومنتج فيديو، ثم أنواع أخرى مثل الصوت والكاروسيل والنشرة والدرس وفق ترتيب المراحل في الخطة.
- تنفيذ Product Layer فوق Artifact وRecipe، بحيث يعرّف المنتج غرضًا وتجربة ومخرجًا أو مجموعة مخرجات وعلاقة بالتوزيع، دون جعل Product بديلًا عن Artifact أو Recipe.
- بناء مسار منتج للصورة ومسار منتج للفيديو على المحرك والحدود العامة، مع Output Contract وstorage/provenance والتحقق لكل نوع. لا يشترط أن يُنفذا داخل الحزمة نفسها، لكنهما جزء من خطة البناء المعتمدة وليسا مؤجلين إلى طلب تجاري خارجي.
- عدم نسخ محرك الإنتاج لكل نوع؛ تُضاف capabilities/providers متخصصة وراء الحدود العامة.

**النجاح:** يثبت النظام قدرته على تشغيل أكثر من وصفة وأكثر من نوع Artifact، ويصبح منتج الصورة ومنتج الفيديو هدفين تنفيذيين صريحين في خارطة الطريق.

## 8. بوابة إغلاق المرحلة (Definition of Done)

لا تُغلق `Production Platform Foundation` حتى تتحقق جميع الفئات التالية:

### معماريًا
- الهوية والسياسة والوصفة وعقد المخرج ليست مفاهيم hard-coded داخل محرك الإنتاج.
- المحرك لا يتعامل مع Telegram بوصفه حقيقة مركزية.
- لا يكون Post هو نوع المخرج الوحيد الذي يعرفه المحرك.
- لا يوجد coupling جديد غير مبرر بين المساحات.
- لا تُضاف بنية تحتية غير لازمة.

### وظيفيًا
- تعمل `BOOK_TO_TELEGRAM_POST` من البداية إلى النهاية.
- تعمل Recipe ثانية دون نسخ المحرك.
- تؤثر الإصدارات الجديدة في Runs الجديدة فقط.
- تحتفظ Runs السابقة بالسياق المثبت.
- لا يمنع فشل عنصر بقية العناصر من الاستمرار عندما تسمح دلالات العملية بذلك.
- يعمل retry/resume/recovery بعد إعادة تشغيل التطبيق.
- تبقى idempotency للنشر محفوظة.

### تشغيليًا
- Browser E2E كامل ناجح.
- Integration E2E مع PostgreSQL ناجح.
- يمر Fake وTelegram من حد توزيع متوافق.
- يمكن تتبع العملية عبر correlation IDs.
- لا تسرب السجلات أسرارًا.
- اختبارات migrations وتطبيقها على البيئة المقصودة ناجحة وفق إجراء إصدار آمن.

### من منظور المستخدم والمنتج
- يفهم المستخدم حالة الإنتاج وتقدمه وأسباب الفشل.
- يمكنه فتح المخرج ومصدره وسياق إنتاجه.
- يمكنه مراجعة واعتماد النتائج ثم نشرها دون فقدان provenance.
- لا تتطلب إضافة وصفة جديدة نسخ المحرك أو تدخلًا برمجيًا في كل تغيير تحريري عادي.
- لا يعتمد مستقبل المنتج على Telegram وحده.

## 9. حدود التنفيذ ومراحل الرؤية

هذا القسم لا يستبعد مكونات من الرؤية، بل يوضح الفرق بين أهداف البناء المعتمدة، والتسلسل الزمني، والقرارات التي تحتاج إلى قرار معماري جديد.

### 9.1 أهداف إلزامية ضمن الرؤية المعتمدة

- بناء Control Plane بإصدارات واضحة للهوية والسياسة والوصفة وPrompt وOutput Contracts.
- بناء سياق إنتاج مثبت، ومحرك وصفات عام، وProduction Runs دائمة قابلة للتتبع والاستئناف.
- بناء Artifact عام يدعم أنواع مخرجات متعددة ولا يجعل Post أو Telegram شرطًا على قلب النظام.
- بناء Product Layer لتمثيل المنتجات التي تجمع الغرض التحريري وتجربة الاستخدام ونوع المخرجات والتوزيع.
- دعم منتجات ومخرجات مختلفة، ومن ضمنها **منتج صورة ومنتج فيديو**، إلى جانب المنتجات النصية، مع بنية تسمح بإضافة الصوت والكاروسيل والنشرة والدرس وغيرها.
- فصل Publication عن Distribution وتثبيت حدود المزودين والقدرات.
- استكمال حدود الأمان والملكية وWorkspace وObservability وفق مراحل خارطة الطريق المعتمدة.
- إثبات العمومية باختبارات متكاملة ووصفات ومنتجات مختلفة، لا بمجرد وجود أسماء كيانات أو واجهات فارغة.

هذه أهداف تنفيذية وليست قائمة أفكار اختيارية. تُبنى بالتتابع وفق الاعتماديات وبوابات القبول، ولا تُسقط بسبب عدم وجود طلب تجاري فوري.

### 9.2 تسلسل التنفيذ

1. إكمال Production Platform Foundation، بما فيه عقود Artifact متعددة الأنواع وRecipe Engine وBrowser E2E.
2. إكمال Product Layer فوق Artifact وRecipe.
3. تنفيذ منتج صورة فعلي بعقد مخرج وتخزين ومصدرية واختبارات.
4. تنفيذ منتج فيديو فعلي بعقد مخرج وتخزين ومصدرية واختبارات.
5. إكمال Distribution Boundary وربط المنتجات بقنوات النشر عبر عقود عامة.
6. استكمال Security / Workspace Boundary وObservability وفق مراحل Foundation Roadmap.
7. تنفيذ المنتجات والوصفات والأنواع الأخرى المذكورة في الرؤية بالتتابع نفسه، مع اختبارات قبول لكل قدرة.

يجوز تعديل ترتيب التنفيذ فقط عندما تثبت مراجعة الاعتماديات أو المخاطر أن ترتيبًا آخر أكثر سلامة؛ ويجب توثيق السبب والنتيجة دون حذف أي هدف معتمد.

### 9.3 ما لا يُنفذ تلقائيًا ضمن هذه الرؤية

- Microservices أو Redis/Kafka/Celery أو بنية موزعة لا تتطلبها خارطة الطريق.
- تنفيذ كود اعتباطي داخل الوصفات أو السياسات.
- إعادة تسمية أو حذف Post، أو إعادة بناء Review/Scheduling/Publication دون سبب معماري موثق.
- نسخ محرك الإنتاج لكل منتج أو نوع مخرج.
- إضافات جديدة خارج أنواع المنتجات والقدرات المحددة في الرؤية الحالية؛ هذه وحدها تحتاج إلى قرار جديد.

### 9.4 قاعدة الحوكمة

> الرؤية المعتمدة تحدد ما يجب بناؤه؛ وخارطة الطريق تحدد متى وبأي ترتيب؛ وبوابات القبول تثبت اكتمال كل مرحلة. لا تُستخدم عبارة «وفق الحاجة» لتأجيل هدف معتمد أو تحويله إلى خيار.

## 11. سجل القرارات

- **D1 — الحفاظ على النظام الحالي:** تبقى `Post` والمراجعة والجدولة والنشر، ويكون الانتقال تدريجيًا.
- **D2 — اعتماد snapshot:** يُعمم مبدأ PR #68 على سياق الإنتاج المطلوب، مع مخطط مضبوط بدل تكرار الحقول بلا نهاية.
- **D3 — Control Plane مرحلي ملتزم:** تُنفذ الهوية والسياسة والوصفة وعقد المخرج ضمن المراحل المعتمدة ويرتبط كل عنصر بمحرك فعلي واختبار قبول؛ لا تُؤجل هذه العناصر بحجة انتظار حاجة خارجية.
- **D8 — مخرجات ومنتجات متعددة الأنواع:** الصورة والفيديو هدفان صريحان في خطة البناء، مع Output Contracts وArtifact وProduct Layer وحدود قدرات قابلة لإعادة الاستخدام؛ ليستا إضافتين مشروطتين بظهور طلب تجاري.
- **D4 — المصدرية جزء من تجربة المستخدم:** لا يكفي تخزينها؛ يجب عرض الحالة والسياق والمصدر والإجراء التالي.
- **D5 — الرحلة الكاملة بوابة قبول:** لا تكفي اختبارات الوحدات أو نجاح API منفردًا.
- **D6 — لا بنية تحتية مبكرة:** لا queues أو خدمات مستقلة دون حاجة تشغيلية مثبتة.
- **D7 — الوثائق السابقة محفوظة:** هذه الوثيقة إضافة توثيقية جديدة، وليست تعديلًا أو بديلًا للوثائق المعمارية السابقة.
