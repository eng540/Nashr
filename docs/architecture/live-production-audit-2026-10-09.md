# فحص النسخة المنشورة — Nashr Production

**الرابط:** https://nashr-production.up.railway.app/
**تاريخ الفحص:** 2026-10-09
**الهدف:** التحقق من المسارات الفعلية، الواجهات، Control Plane، والبيانات التشغيلية المنشورة.

## الخلاصة

النسخة المنشورة تعمل كنظام فعلي وليست واجهة شكلية:

- `/control` يعمل ويعرض Control Plane الحقيقي.
- Prompt `editorial.drafter` موجود وإصداره الفعال هو **v5 PUBLISHED**.
- الإصدارات v1–v4 مؤرشفة.
- `/posts/workspace` يعمل ويعرض بنك المنشورات والإنتاج والمراجعة.
- `/publishing` يعمل ويعرض المنشورات المؤهلة وخطط النشر والتقويم.
- API يعيد بيانات إنتاج حقيقية: منشورات، مصادر، وخطط نشر مكتملة.

لا يوجد ما يغير اتجاه وثيقة `Production Platform Foundation`، لكن الفحص يضيف بوابة تشغيلية مهمة: يجب أن تنتقل المرحلة التالية من مجرد اكتمال العقود إلى إثبات أن الـRun والـprovenance قابلان للعرض والتتبع داخل النسخة المنشورة.

## الحالة التشغيلية المرئية

أظهر `/publishing`:

- **9** منشورات معتمدة ومؤهلة للنشر.
- **28** خطة نشر محفوظة.
- **0** عناصر قادمة في التقويم وقت الفحص.

وأظهر API:

- `/posts`: أكثر من **1400 منشور**، منها منشورات `APPROVED` و`PUBLISHED`.
- `/schedules`: خطط مكتملة، منها خطة تحتوي 11 عنصرًا منشورًا بنجاح.
- `/sources`: مصادر مستخرجة بمئات المواد، إضافة إلى مصادر `FAILED` و`STORED` لم تكتمل.

وجود حالات `FAILED` و`STORED` ومواد pending يؤكد أن النظام يملك واقعًا تشغيليًا حقيقيًا يحتاج إلى إدارة دورة حياة، وليس مجرد demo ناجح.

## Control Plane

تم فتح واجهة `/control` واختيار قالب المحرر:

- القالب: `editorial.drafter`
- الإصدار الفعال: `v5 · PUBLISHED`
- الإصدارات السابقة: `v1` إلى `v4` بحالة `ARCHIVED`
- الواجهة تعرض النص الفعلي وأزرار حفظ المسودة ونشر النسخة.

هذا يثبت أن Control Plane متصل بالـruntime والبيانات، وليس مجرد شاشة ثابتة.

PR #68 يضيف pinning للـPrompt داخل `ProductionJob`، لكن الواجهة الحالية لا تعرض بعد snapshot الخاص بالـJob أو الـRun للمستخدم. هذه هي الفجوة التشغيلية التالية في provenance.

## الأداء في الفحص الأولي

قياس طلب واحد لكل مسار أساسي أعطى تقريبًا:

| المسار | الزمن المقاس |
|---|---:|
| `/` | 9.20s |
| `/health` | 4.03s |
| `/control` | 5.36s |
| `/posts/workspace` | 8.65s |
| `/publishing` | 5.12s |
| `/api/control/prompts` | 2.63s |
| `/posts` | 2.08s |

هذه قياسات أولية قد تتأثر بـ cold start وRailway والاتصال الخارجي، ولا تكفي وحدها للحكم على throughput. لكنها كافية لإضافة بند performance baseline إلى المرحلة التالية، خصوصًا أن فتح `/posts/workspace` و`/publishing` يطلق طلبات إضافية بعد تحميل shell.

## النتائج التي تغير ترتيب التنفيذ

### يجب إدراجها في المرحلة التالية

1. **Production Run observability:** عرض Run ID، حالته، تقدمه، وإصدارات السياق التي أنتجت النتيجة.
2. **Prompt provenance UI:** إظهار Prompt version المثبت للـJob/Run، لا الاكتفاء بعرض النسخة النشطة حاليًا.
3. **Lifecycle dashboard:** فصل واضح بين `FAILED` و`STORED` و`PENDING` و`COMPLETED` مع إجراء تالي للمستخدم.
4. **Performance baseline:** قياس cold/warm، زمن API، زمن تحميل الواجهة، وطلبات الصفحة.
5. **Root route:** إما redirect إلى `/posts/workspace` أو صفحة دخول واضحة بدل 404.
6. **Readiness check:** `/health` الحالي لا يثبت جاهزية قاعدة البيانات أو runtime dependencies.

### لا تغير اتجاه الرؤية

- لا حاجة لإعادة بناء Post.
- لا حاجة لإعادة بناء Scheduling.
- لا حاجة لإضافة Microservices أو Queue infrastructure.
- لا حاجة لبناء Identity/Policy/Recipe كاملة قبل وجود consumer.
- لا تزال `Production Platform Foundation` هي المرحلة الصحيحة.

## بوابة قبول إضافية للمرحلة

تُعتبر المرحلة التالية مكتملة فقط عندما يستطيع المستخدم من الواجهة:

1. تشغيل Recipe وإنشاء Run.
2. رؤية الـRun وحالته وتقدمه.
3. فتح Artifact/Posts الناتجة.
4. رؤية المصدر والـKnowledge unit والـPrompt/Recipe/Policy versions.
5. إعادة المحاولة مع الحفاظ على snapshot القديم.
6. معرفة سبب فشل العناصر ومعالجتها.
7. الانتقال من النتائج المعتمدة إلى النشر دون فقدان provenance.

## حدود الفحص

- لم يتم تنفيذ عمليات POST/PATCH/Publish على بيانات الإنتاج حتى لا يتم تعديل المحتوى أو نشر Prompt أو إرسال Telegram دون طلب صريح.
- لا يمكن إثبات pinning التاريخي للـJobs من الواجهة الحالية لأن API لا يعرض حقول Prompt snapshot في Job detail؛ تم التحقق منه من كود `main` وPR #68.
- لم يتم اعتبار OpenAPI أو API العامة آمنة تجاريًا؛ هذا سجل ملاحظة جاهزية، وليس عائقًا لتقييم مسار التطوير الحالي.
