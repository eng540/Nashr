# Architecture Gate — Post PR #53

Date: 2026-10-08
Main HEAD: 89d672a24783099e6d586f501baada7e9a6be363

## Scope

Verify the actual main after PR #53 and decide whether Nashr is ready to move Review/Scheduling ownership toward Artifact, or needs a smaller hardening step first.

## Evidence inspected

- PR #53: Artifact Consumption in Publication.
- Current Artifact domain/application modules.
- Production Job Runner.
- Review application.
- Publication application/domain.
- Scheduling application and execution path.
- Persistence models for Post, Publication and ScheduleItem.
- API routes for posts/publication/scheduling.
- Frontend foundation package and existing E2E-oriented contracts.
- Existing architecture baseline and previous gates.

## Findings

### 1. Artifact

**PASS / KEEP**

Artifact is a small provider-neutral domain contract:

- identity
- source knowledge unit identity
- kind
- content
- editorial status
- timestamps

It has no Telegram dependency.

### 2. Production

**PASS / KEEP**

Production still persists the current Post representation, but exposes the result through the Artifact adapter. Production Job completion records the artifact identity while preserving existing post persistence.

No schema rewrite is required.

### 3. Publication

**PASS WITH HARDENING**

PR #53 made Publication a real Artifact consumer:

- Telegram draft creation can consume Artifact.
- Approval/publication can receive an explicit Artifact.
- Artifact content is used for the publication payload.
- Artifact approval is enforced before publication.

However, `ApproveAndPublish` still has a compatibility fallback that loads `PostModel` when no Artifact is supplied. It also contains direct Post checks in the optional content-edit path.

Therefore the boundary is real, but not yet clean enough to declare Post removed from the Publication application boundary.

This is a **small controlled refactor**, not a reason for a schema migration.

### 4. Review

**KEEP / DEFER**

Review correctly remains Post-centric:

- Post owns DRAFT / APPROVED / REJECTED.
- Editing returns the Post to DRAFT.
- Pending schedule items are cancelled when editorial content changes.
- Processing items are protected from editorial mutation.

Moving Review now would combine editorial ownership changes with publication boundary cleanup.

Do not move it yet.

### 5. Scheduling

**KEEP / DEFER**

Scheduling remains Post-centric for:

- schedule item identity
- eligibility
- persistence
- schedule UI/API payloads

But the execution path now converts the selected Post to Artifact before publication.

The critical safety invariants remain present:

- final APPROVED check immediately before publication
- already-PUBLISHED → SKIPPED
- idempotency/concurrency protection
- durable schedule state
- no open DB transaction around Telegram provider calls

Do not migrate Scheduling ownership yet.

### 6. API / Browser boundary

**PASS / KEEP**

No API/browser contract migration is required by PR #53.

The existing frontend foundation and workspace separation remain compatible with the current Post-centric review/scheduling APIs.

No frontend rewrite should be bundled with the next Artifact refactor.

### 7. Distribution

**PASS / KEEP**

Telegram remains an external adapter.

Artifact and Publication domain contracts remain provider-neutral.

### 8. Data ownership

**KEEP**

Current ownership is intentionally:

- Post → editorial persistence/state
- Artifact → generic production output contract
- Publication → distribution ledger
- Schedule → timing/execution state

Do not introduce `artifact_id` persistence merely to make the model look more target-like.

## Decision Matrix

| Area | Decision | Reason |
|---|---|---|
| Artifact domain | KEEP | Stable provider-neutral boundary |
| Production → Artifact | KEEP | Working incremental boundary |
| Publication → Artifact | KEEP + HARDEN | Real consumer, but compatibility coupling remains |
| Post persistence | KEEP | Still owns current editorial state |
| Review | KEEP / DEFER | Correctly Post-owned today |
| Scheduling | KEEP / DEFER | Correct persistence and safety invariants |
| Telegram adapter | KEEP | Correct distribution boundary |
| API/browser contracts | KEEP | No migration needed |
| Identity | DEFER | Not required for current capability |
| Recipe | DEFER | Not required for current capability |
| Product | DEFER | Premature |
| artifact_id migration | PROHIBIT NOW | No operational need |
| Post removal/rename | PROHIBIT NOW | Would mix ownership migrations |
| Queues/workers/microservices | PROHIBIT NOW | No evidence requires them |
| Telegram in Artifact/Domain | PROHIBIT | Violates provider boundary |

## Gate Outcome

**PASS WITH CONTROLLED REFACTOR**

Nashr is not blocked by PR #53.

But the next implementation should **not** be Review/Scheduling migration.

The next PR should harden the Publication Artifact boundary:

### Next PR — Harden Publication Artifact Boundary

Required scope:

1. Make Artifact the explicit internal input to publication logic.
2. Keep Post → Artifact conversion at the application edge/adapter.
3. Remove duplicated direct PostModel checks from the core publication path where behavior can be expressed through Artifact.
4. Preserve compatibility at the API/application edge.
5. Preserve:
   - APPROVED gate
   - publication idempotency
   - PUBLISHED → SKIPPED
   - post_id persistence
   - current API/browser contracts
6. Add focused characterization/regression tests.
7. No migration.
8. No Review refactor.
9. No Scheduling ownership refactor.
10. No Identity/Recipe/Product.

### Exit condition

Only after this hardening PR passes its tests should another Architecture Gate decide whether Review or Scheduling should consume Artifact more directly.

## Explicit non-goals

This gate does not authorize:

- replacing Post with Artifact;
- creating an Artifact database table;
- adding artifact_id to all persistence;
- redesigning Review;
- redesigning Scheduling;
- introducing a generic content-management abstraction;
- introducing distributed workers;
- introducing Identity/Recipe/Product;
- changing frontend architecture.
