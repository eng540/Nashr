## Current reality
### Frontend
React + TypeScript + Vite + Tailwind + TanStack Query + Playwright now form the production frontend foundation for /publishing and /posts/workspace. The backend API remains the business contract.

### Production
The production path is still Post-centric: KnowledgeUnit → ProducePost → PostModel. ProductionJobItem stores post_id, and the runner delegates each material to Post production.

### Review
Editorial review is a human gate, but its aggregate is still Post. Approval/rejection changes Post state.

### Publication
Publication is durable and has a domain object, but it still carries post_id and knowledge_unit_id. Telegram is behind a publisher port while the current application flow remains Telegram-specific.

### Scheduling
ScheduleItem is keyed to post_id and performs the final APPROVED check immediately before publication. This safety invariant must remain during refactoring.

## Required next boundary
Artifact Boundary is the next implementation target, introduced as a compatibility-preserving domain/application boundary, not a schema rewrite.

Intended transition:
Knowledge → Production Run → Artifact → Review → Publication → Distribution

The existing Post remains the first concrete artifact representation for the current Telegram workflow.

## Constraints for the next PR
1. Do not delete or rename Post.
2. Do not break existing Post APIs or browser journeys.
3. Do not introduce Identity or Recipe configuration yet.
4. Introduce a minimal Artifact contract at the domain/application boundary before changing persistence ownership.
5. Production must expose a generic production-result/artifact boundary rather than forcing callers to understand Telegram publication.
6. Review continues to gate the concrete current artifact/Post.
7. Scheduling continues to require APPROVED and preserves idempotency and PUBLISHED→SKIPPED behavior.
8. Publication consumes the approved artifact representation while Telegram remains an adapter.
9. No queue/worker infrastructure.
10. Add characterization tests around the current Post path before moving ownership.

## Keep / Refactor / Add / Prohibit
### KEEP
FastAPI, SQLAlchemy, PostgreSQL, Alembic, durable jobs, provenance, Book Map, Gemini adapters, Review gate, scheduling idempotency, Telegram adapter, React frontend, existing API/E2E contracts.

### REFACTOR
Post-centric coupling between ProductionJobItem, production application services, Publication and ScheduleItem. Refactor incrementally behind stable contracts.

### ADD
A minimal domain/application Artifact boundary and explicit production-result contract, with tests proving current Post behavior remains unchanged.

### PROHIBIT NOW
Identity runtime, Recipe engine, Product model, second distribution platform, microservices, queue infrastructure, vector/graph storage, and frontend rewrites outside migrated workspaces.

## Gate outcome
PASS — proceed to the Artifact Boundary implementation PR.

This gate does not authorize a schema rewrite. The next PR must prove the boundary first and migrate persistence only where evidence requires it.
