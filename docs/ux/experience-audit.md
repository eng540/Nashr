**المستودع:** `eng540/Nashr`

هذه الوثيقة لا تستبدل وثائق المعمارية ولا تغيّر ملكية المجالات. هدفها أن تربط تجربة المستخدم بسلوك النظام الفعلي، وأن تميز بين الحقائق المثبتة بالكود والقرارات المقترحة وما لم يُتحقق منه بعد.

## 2. خريطة مساحات المنتج

المساحات منفصلة عمدًا:
- **المكتبة / Console:** المصادر، تحليلها، المعرفة، خريطة الكتاب، والمواد.
- **مصنع المحتوى:** إعداد مطالبات الإنتاج، متابعة ProductionJob وعناصره، مخرجات الإنتاج، تحرير المنشورات ومراجعتها واعتمادها.
- **النشر:** المحتوى المعتمد والمؤهل، خطط النشر، عناصر الخطط، والتقويم.
- **التحكم / Control Plane:** المنتجات والوصفات والهويات والسياسات وعقود المخرجات والقوالب وإصداراتها.

المسار المفاهيمي:
`Source → Knowledge/Inventory → Production Claim/Job → Recipe/Capability → Artifact/Post → Review/Approval → Scheduling/Publication → Distribution`

هذا المسار يصف حدود النظام؛ لا يعني أن جميع أنواع المخرجات اجتازت اختبار قبول حيًا شاملًا.

## 3. حقائق مؤكدة من الكود عند نقطة الأساس

### 3.1 مصنع المحتوى

في `frontend/src/features/post-bank/PostBankPage.tsx` يجتمع في مكوّن واحد:
- مرشحات بنك المنشورات والبحث والفرز والترقيم.
- اختيار المنتج والهوية والمصدر ونطاق الإنتاج.
- اختيار محور أو مواد.
- إنشاء مطالبة الإنتاج مع `idempotency_key` محفوظ في localStorage عند غموض نتيجة الإرسال.
- متابعة حالة المهمة وتقدمها وعناصرها.
- عرض أخطاء المهمة وعناصرها، وتشخيص نتيجة المزوّد غير المحسومة.
- استئناف المهمة عبر `productionJobsApi.resume` عندما يقرر API أن الإجراء التالي `RETRY_FAILED_ITEMS`.
- سياق التنفيذ المثبّت، بما فيه prompt والوصفة والمنتج وعقد المخرج والسياسة والهوية.
- تحرير المنشورات ومراجعتها واعتمادها/رفضها واعتماد مجموعة من المنشورات.
- الانتقال إلى مساحة النشر.
- `GenericArtifactReviewPanel` لمراجعة المخرجات غير القائمة على منشورات Telegram.

إذن، الخلط بين أهداف الصفحة **حقيقة بنيوية مؤكدة** في نقطة الأساس؛ أما مقدار أثره على كل مستخدم فيحتاج إلى اختبار قابلية استخدام.

### 3.2 عقود دورة حياة الإنتاج

المراجع:
- `app/domain/production_jobs.py`
- `app/application/production_jobs.py`
- `app/api/routes.py`
- `frontend/src/shared/api/productionJobsApi.ts`

الحالات المعرفة للمهمة: `QUEUED`, `RUNNING`, `COMPLETED`, `FAILED`.  
الحالات المعرفة للعنصر: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`.

المهمة لا تملك حالة مستقلة اسمها “تحتاج تسوية”. الحالات غير المؤكدة ممثلة كعناصر فاشلة مع رموز مثل `PROVIDER_OUTCOME_UNKNOWN` أو `PRODUCTION_OUTPUT_RECONCILIATION_REQUIRED`، ويحسبها API في `reconciliation_required_items`. لذلك يجب ألا تترجم الواجهة كل `FAILED` إلى “أعد المحاولة”؛ قد تكون إعادة المحاولة غير آمنة.

الـAPI يوفّر إنشاء المهمة، قراءة الحالة، قراءة العناصر بصفحات، ومسار `resume` مع `retry_failed`. لم يظهر في نموذج الحالة أو مسارات API التي فُحصت endpoint لإيقاف/إلغاء/إيقاف مؤقت لمهمة الإنتاج. **لا تعرض أزرار إلغاء أو إيقاف مؤقت أو استئناف عام**؛ الموجود هو استئناف مشروط عبر المسار المخصص، وتحدده `next_action`.

تحدد واجهة API `next_action` وفق الحالة وعدد العناصر: `WAIT`, `RETRY_FAILED_ITEMS`, `INSPECT_FAILURE`, `REVIEW_DRAFTS`, `NONE`. يجب أن تكون هذه الإشارة مرجع الإجراءات، مع احترام قيد نتيجة المزوّد غير المؤكدة.

### 3.3 النشر والمراجعة

- المنشورات التحريرية تملك حالات `DRAFT`, `APPROVED`, `REJECTED`، والمراجعة والتحرير يعتمدان على Post.
- المخرجات العامة لها مسار مستقل عبر `GenericArtifactReviewPanel` وحالات `DRAFT`, `APPROVED`, `REJECTED`، مع معاينة للصورة والفيديو والصوت عندما يتوفر رابط الوسيط.
- `PublishingPage.tsx` يفصل بالفعل بين «المنشورات الجاهزة» و«خطط النشر» و«التقويم»، ويدعم البحث والتصفية والترقيم والتحديد وإنشاء الخطة وإجراءات الخطة بحسب حالتها.
- أفعال الخطط المدعومة في الواجهة وعقود API تشمل التفعيل والإيقاف المؤقت والإلغاء وإعادة محاولة العناصر الفاشلة، كما توجد إعادة محاولة على مستوى عنصر.
- لا تختبر هذه المهمة أي إرسال خارجي حقيقي، ولا تستخدم Telegram.

### 3.4 اختيارات المواد

في `productionJobsApi.ts`، `BookMap` يعيد `topics` و`materials` كقائمتين منفصلتين. يجب أن تعتمد قائمة الاختيار على `bookMap.materials` حتى لا تختفي المواد التي لا تنتمي إلى محور.

في الخلفية، `SOURCE` يختار جميع المواد المرتبطة بالمصدر، و`TOPIC` يختار مواد المحور المرتبطة بالمصدر، و`SELECTION` يتطلب معرفات مواد غير مكررة تنتمي جميعها إلى المصدر. إذا لم ينتج النطاق مواد، يرفض الخادم إنشاء المهمة.

**دلالة مهمة:** مرشح الواجهة `productionMode` يحدّد الكتب/المحاور/المواد المعروضة، لكنه ليس جزءًا من طلب الإنتاج. عند اختيار نطاق `SOURCE`، يحدد الخادم جميع مواد المصدر. يجب أن يصرّح ملخص ما قبل التشغيل بذلك بوضوح وألا يوحي أن مرشح “يحتاج إنتاجًا” سيجعل الخادم يختار المواد المتبقية فقط. إذا أراد المنتج مستقبلًا دعم “المواد غير المنتجة فقط” كنطاق تنفيذي، فذلك قرار وعقد API منفصلان، وليس تغييرًا ضمنيًا في الواجهة.

## 4. تصنيف نتائج التدقيق

### مشكلات مؤكدة
1. إعداد الإنتاج، مراقبة المهمة، بنك المنشورات، تحرير المنشور، والمراجعة العامة موجودة معًا في `PostBankPage.tsx`؛ الفصل البصري بين الأهداف محدود.
2. الحالات التقنية للمهمة والعناصر تظهر في الواجهة الأساسية بصيغتها التقنية، بينما يجب تقديم تسمية مفهومة مع إبقاء الرمز في التشخيص.
3. تفاصيل السياق المثبت وprompt body معروضة ضمن تفاصيل المهمة؛ هي مفيدة للتدقيق، لكنها مطولة للاستخدام اليومي.
4. `SOURCE` في الخادم يعني كل مواد المصدر، وليس فقط المواد التي يعرضها مرشح “يحتاج إنتاجًا”.
5. نموذج المهمة لا يدعم إلغاءً أو إيقافًا مؤقتًا مستقلًا وفق الكود والمسارات التي فُحصت.

### تحسينات مقترحة، لا حقائق عن عطل
1. تحويل إعداد الإنتاج إلى خطوات: المنتج/الهوية، المصدر/النطاق، مراجعة الإعدادات.
2. فصل إعداد الإنتاج عن متابعة المهام والمراجعة/بنك المحتوى.
3. عرض الحالات بالعربية، مع إبقاء المعرفات والتفاصيل الفنية في قسم متقدم.
4. توحيد حالات التحميل والخطأ والنتيجة الفارغة ورسائل النجاح.
5. اختبار رحلة كاملة على سطح المكتب والهاتف واتجاه RTL.

### أمور لم يجر التحقق منها بصريًا أو تشغيليًا
- المظهر الفعلي على الهاتف وأحجام العرض المختلفة.
- استخدام لوحة المفاتيح والتركيز وقارئ الشاشة.
- أداء التحديثات على اتصال بطيء أو انقطاع حقيقي.
- سلوك الواجهة في Railway؛ هذه المهمة تمنع الوصول إلى Railway أصلًا.
- قبول جميع أنواع المخرجات من الإنتاج إلى المراجعة بعد إعادة تحميل الصفحة.
- تشغيل الاختبارات محليًا؛ ستسجل نتيجة CI بعد فتح PR منفصلة عن التحقق التشغيلي.

## 5. مبادئ تجربة Nashr

1. **التدفق قبل الزينة:** نظّم القرار والعمل قبل تعديل الألوان والمسافات.
2. **لا فقدان للوظائف:** انقل الوظيفة إلى موضعها الصحيح بدل حذفها.
3. **الخادم مصدر الحقيقة:** لا تعرض إجراءً أو حالة لا يدعمها الخادم.
4. **الاختيارات التابعة للسياق:** تغيير المصدر يزيل المحور والمواد التابعة له بوضوح؛ تحديث بيانات المنتج وحده لا يمسح الاختيار الصالح.
5. **النطاق صريح:** وضّح الفرق بين كل مواد المصدر، مواد محور، ومواد محددة.
6. **الأمان عند غموض النتيجة:** لا تعاود طلبًا مدفوعًا إذا كان قبول المزوّد غير مؤكد؛ اعرض الحاجة إلى التسوية.
7. **معلومة يومية ثم تشخيص متقدم:** حالة المهمة والتقدم والخطوة التالية أولًا، والتفاصيل الداخلية عند الطلب.
8. **اللغة العربية وRTL أساس:** اتجاه صحيح وتسلسل مفهوم ولمس مناسب، لا معالجة لاحقة.
9. **لا تغيير معمارية بلا مستهلك حقيقي:** لا تعِد ملكية Post/Artifact/Review/Scheduling أو تضف طابورًا جديدًا لتحسين الواجهة.
10. **لا نشر حقيقي في اختبارات تجربة المستخدم:** كل الاختبارات على بيانات اصطناعية واعتراضات API آمنة.

## 6. التدفق المستهدف

### مصنع المحتوى
1. **اختيار المنتج والهوية:** منتجات ذات إصدار منشور/نشط فقط وفق API؛ الهوية اختيارية عندما يسمح العقد بذلك.
2. **اختيار المصدر والنطاق:** كتاب ثم `SOURCE` أو `TOPIC` أو `SELECTION`; تُمسح اختيارات المحور/المواد التابعة عند تغيير المصدر أو النطاق.
3. **مراجعة الإعدادات:** ملخص المنتج والمصدر والنطاق وعدد المواد الحقيقي وما سيشمله الطلب.
4. **بدء الإنتاج:** إنشاء مطالبة مع مفتاح idempotency؛ عند غموض الرد يعاد استخدام المفتاح نفسه ولا تُنشأ مطالبة مختلفة بصمت.
5. **متابعة المهمة:** حالة وتقدم وعدد عناصر ونتائج وأخطاء وإجراء تالي مستند إلى `next_action`.
6. **مراجعة المخرجات:** منشورات Post في مراجعتها المعتادة، والمخرجات غير المنشورية في المراجعة العامة.
7. **بنك المحتوى:** بحث وفلاتر وتحديد واعتماد وانتقال واضح إلى النشر للمحتوى المؤهل.

### النشر
المحتوى المعتمد والمؤهل → تحديد النطاق → فحص الأهلية → إعداد الخطة → مراجعة الإعدادات → حفظ الخطة → تفعيلها عند الحاجة → متابعة العناصر والتقويم. يجب أن تبقى الجاهزية والخطة والتقويم مفاهيم منفصلة.

## 7. قواعد عرض الحالات والأخطاء

| الحالة/المعلومة التقنية | العرض المطلوب |
|---|---|
| `QUEUED` | «في انتظار بدء التنفيذ» |
| `RUNNING` | «قيد التنفيذ» مع التقدم والعناصر الجارية |
| `COMPLETED` | «اكتملت المهمة» مع الانتقال للمراجعة |
| `FAILED` بلا تسوية | «تعذرت المهمة» مع السبب والإجراء المسموح |
| `PROVIDER_OUTCOME_UNKNOWN` أو reconciliation-required | «نتيجة المزوّد غير محسومة — يلزم التحقق قبل إعادة المحاولة»؛ لا تعرض retry العادي |
| `PENDING/RUNNING/COMPLETED/FAILED` للعنصر | ترجمة واضحة بجوار كل مادة |
| `error_code` | في التشخيص المتقدم، مع رسالة مبسطة وإجراء مدعوم في الواجهة الأساسية |
| `resolved_context` وprompt body | تفاصيل متقدمة قابلة للفتح، مع إبقاء تحذير السياق غير الصالح ظاهرًا |

لا تعتبر المهمة “مكتملة بالكامل” إذا فشلت بعض العناصر لمجرد أن حالة المهمة نهائية؛ اعرض العدّادات الفعلية.

## 8. معايير القبول

- يستطيع المستخدم الانتقال بين خطوات الإعداد دون فقد اختيار صالح.
- لا يمكن الوصول إلى المراجعة والبدء قبل استيفاء المنتج والمصدر والنطاق الفعلي.
- العدد المعروض مشتق من البيانات المحملة، وليس رقمًا تقديريًا.
- يوضح ملخص `SOURCE` أن الطلب يشمل جميع مواد المصدر.
- المحور من الكتاب نفسه، والمواد تأتي من قائمة المواد المستقلة، بما فيها غير المصنفة.
- لا يمكن بدء `TOPIC` دون محور صالح أو `SELECTION` دون مادة واحدة على الأقل.
- لا يظهر إجراء إعادة محاولة إلا وفق `next_action` ولا يُعاد إرسال مطالبة غامضة بمفتاح جديد تلقائيًا.
- تبقى مراجعة المنشورات ومراجعة Artifact العامة وبنك المحتوى ومساحة النشر قابلة للوصول.
- لا تتغير عقود API أو ملكية النماذج بلا مبرر واختبارات.
- تغطي اختبارات المتصفح التدفق الجديد وحالات الاختيار؛ وCI دليل منفصل عن الفحص البصري/الإنتاجي.
- لا Railway، لا Telegram، ولا نشر خارجي حقيقي خلال المهمة.

## 9. قرارات مفتوحة لا تُحسم ضمنيًا

- هل نضيف نطاقًا تنفيذيًا مستقلاً “المواد غير المنتجة فقط”؟ يتطلب قرار منتج وتغيير API/الخادم واختبارات، وليس مرشح واجهة فقط.
- هل نحتاج إجراءً إداريًا لتسوية نتائج المزوّد غير المؤكدة؟ حاليًا لا يجوز تجاوز الحماية بإعادة المحاولة.
- هل تُفصل المهام إلى صفحة مستقلة أم تبويب داخل مصنع المحتوى؟ يجب أن يحافظ القرار على السياق والوظائف ويثبت باختبارات استخدام، دون إنشاء صفحات غير لازمة.


## 10. شريحة التنفيذ الحالية — PR #127 (غير مدمج)

في الفرع `feat/content-factory-ux-workflow`، أُضيفت أقسام واضحة داخل مصنع المحتوى: إعداد الإنتاج، متابعة المهمة الحالية، وبنك المحتوى والمراجعة. إعداد الإنتاج أصبح رحلة من ثلاث خطوات مع ملخص قبل التشغيل؛ وعند نجاح إنشاء المطالبة تنتقل الواجهة إلى متابعة المهمة. تُعرض الحالات الأساسية بالعربية، ويظهر تنبيه خاص للعناصر التي تتطلب تسوية نتيجة مزوّد غير محسومة.

هذه التغييرات في PR #127 ولم تُدمج بعد. وجود الكود لا يثبت اجتياز build أو Playwright أو تحقق بصري. راجع `implementation-log.md` لمعرفة SHA الحالي ونتائج CI الفعلية قبل استكمال المرحلة التالية.


اختيار المواد في PR #127 أضيف إليه البحث بالعنوان، والفلترة بنوع المادة، وترقيم الصفحات، وتحديد الصفحة وإلغاء تحديدها ومسح التحديد. يوضح العرض بقاء العناصر المختارة خارج المرشح الحالي. هذه الإضافة غير مدمجة؛ راجع أحدث CI في سجل التنفيذ قبل اعتمادها.


## 11. Follow-up correction — wizard dependency order (2026-10-12)

A review of PR #127 found a confirmed sequencing defect in the first implementation: the final review step still rendered the topic selector and the manual-material picker. That forced scope choices to happen during review, contrary to the target flow.

The implementation now places the topic selector and all SELECTION controls (type filter, title search, pagination, page selection/deselection, and retained cross-filter selection) in **step 2: source and scope**. Step 3 is explicitly **“مراجعة إعداد الإنتاج”** and contains the review summary, edit-back action, and explicit start action only.

Transition readiness is derived from shared predicates rather than divergent inline checks:
- Product and identity options must load successfully; the product and selected identity must be active, and the product's configured recipe must have an active version.
- The source must be selected from current valid source options and its book map must load successfully.
- SOURCE requires a non-empty actual source material list; TOPIC requires a valid topic belonging to the selected book with materials; SELECTION requires at least one selected ID and every selected ID must belong to the current source.
- Loading/error states block review and start. Failed option queries expose retry actions.
